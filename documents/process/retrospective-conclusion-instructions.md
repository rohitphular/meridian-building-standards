# Retrospective Conclusion Instructions

The scrum master reads both party retrospectives and writes a synthesis conclusion. This is a process analysis, not a technical review.

---

## Steps

1. **Read both retrospectives.** Identify recurring themes across both parties.

2. **Identify process gaps.** For each gap:
   - Name it (G[N] format)
   - Describe what happened (specific incident, not a generalisation)
   - Explain why prior fixes did not prevent it (the root cause, not the symptom)
   - State the fix applied

3. **Identify what worked.** List practices to continue into the next epic.

4. **Write action items.** Per party, specific and time-bound. If an action has no owner it will not happen.

5. **Update process files.** If a gap requires a change to an instruction or template file, make the change and record it in the conclusion. Only update process files when the gap reflects a missing rule — something that should always be done but is not yet documented. Scope creep, domain knowledge, and one-off workarounds do not update process files. Changes made in this step take effect immediately for the next epic; no separate review round is required.

---

## Rules

- **Ignore technical content.** The conclusion is about process failures, not domain correctness.
- **Name the root cause, not just the symptom.** "The gate was skipped" is a symptom. "The gate had no escalation protocol when blocked" is a root cause.
- **Every gap must have a fix.** An observation without an actionable fix is not a gap.
- **Record every file updated.** The conclusion must include a table of every process file changed and what was changed.
